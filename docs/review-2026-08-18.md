# Field review — 2026-08-18

A full-repo review against the stated goal — *an installable software factory for
any project, greenfield or brownfield* — taken together with the first field run
against a real brownfield project (personal-finance-coach, see commit `c7e93af`).
Findings were verified by experiment where possible, not asserted. This document is
the durable record: each finding names its evidence, its disposition, and the change
it is expected to land in, so a later agent can pick any of them up without
re-deriving the argument.

Written while `reposition-gatedloop` was mid-implementation (38/45, subagent active),
which constrains what could be edited today — see "Coordination" at the end.

## Verdict, in one paragraph

The two-axes architecture (stack → `.gates.yaml`, workflow shape → OpenSpec schema,
gatedloop owns only the loop) is sound and defensible, and the repo's self-diagnosis
(`AUTOMATION.md`) is accurate. The gap between the pitch and the product is exactly
the enforcement layer `harden-unattended-loop` plans — plus one **confirmed defect
in the deterministic selection layer** that harden would silently inherit, and an
onboarding surface that asks six manual steps where one guided command is possible.
The findings below are ordered by how much they threaten the factory claim.

## Findings

### F1 — CONFIRMED: the blocking live-check gate is vacuous at merge time

`_changed_files` (`bin/gates`) computes the hot set from `git diff HEAD` + staged +
untracked. At change completion (tdd-apply §7.5) — all tasks committed, tree clean —
that set is **empty**, so `gates run live-check` prints *"no live-check for the hot
surfaces — skipping (not a failure)"* and exits 0. Reproduced in a scratch repo
whose single catch-all surface had `live-check: "echo LIVE-CHECK-RAN && false"`:
after committing everything, the always-failing probe exited 0 without running.

This is precisely the silent-skip class the shim's own docstring says it exists to
prevent. The changed-set baseline for **change-level** gates must be the change's
diff against the merge target (`git diff main...HEAD`, ∪ working set), not the
working tree. Note the two call sites legitimately want different baselines:

| Call site | Wants | Today gets |
|---|---|---|
| per-task `gates rules` / convention review (§5f) | this task's diff | working-tree diff — **correct** |
| completion `gates run live-check` (§7.5) | the whole change's diff | working-tree diff — **empty, vacuous pass** |

The fix must live in `bin/gates` defaults, not in a prompt-remembered flag —
relying on the skill to pass `--changed`/`--all` is the failure mode this repo is
built against. **`harden-unattended-loop` D2 inherits this**: its merge marker
records "live-check green on branch-head tree," which a vacuous pass satisfies.
The selection fix is a hard prerequisite of harden.

**Disposition: landed in `fix-change-scope-selection`.** `cmd_run`'s `live-check`
path now selects the union of the working set and the branch's merge-base diff
against the resolved merge target (design D1/D2); the F1 reproduction above is
pinned as `tests/test_selection.py::TestF1LiveCheckVacuousOnCleanBranch`, red
against the unmodified shim and green after the fix.

### F2 — rule-id resolution is a substring check

`gates validate` resolves a rule-id with `rule not in doc_text`
(`bin/gates:280`). Any mention of the id anywhere in the doc — prose, a comment,
"we removed stack-agnostic-prompts" — counts as resolved, so a dangling id can
validate green. It should require a `### <id>` heading match; `parse_conventions_doc`
already parses exactly those headings twenty lines down.

**Disposition: landed in `fix-change-scope-selection`.** `_errors` now resolves
rule-ids against `_heading_ids` (`### <id>` headings only, relaxed to not require
`Applies to:`/`Rule:` metadata); the substring check is deleted. Covered by
`tests/test_manifest.py::TestRuleIdHeadingResolution`.

### F3 — glob matching over-matches

`_matches` collapses `**` → `*` and uses `fnmatch`, whose `*` crosses `/` — so
`*.md` matches `docs/deep/x.md`. Failure direction is safe (surfaces run hotter
than declared), but selection is the one deterministic job; either fix the
semantics or document fail-hot as intended.

**Disposition: landed in `fix-change-scope-selection`.** Decision (design D5) was
to keep `fnmatch` rather than add a new safety-critical matcher, document the
fail-hot contract explicitly in `SETUP.md`'s surfaces section, and pin the error
direction with `tests/test_selection.py::TestGlobMatchingIsFailHot` so a future
change to `_matches` cannot silently start under-matching.

### F4 — the selection logic is the least-tested safety-critical code

`tests/` covers manifest parsing and conventions sync; nothing covers
`_changed_files`, `hot_surfaces`, `_matches`, or `cmd_run`'s live-check path. A
test asserting "clean tree on a branch still selects the change's surfaces" would
have caught F1. Selection tests belong in the same change as F1–F3.

**Disposition: landed in `fix-change-scope-selection`.** `tests/test_selection.py`
now covers `_changed_files`/`_working_set_files`, `_resolve_merge_target`,
`_change_level_changed_files`, `hot_surfaces`, `_matches`, and `cmd_run`'s
live-check path, including the clean-tree-on-branch case that would have caught
F1 and a non-`main` default branch resolved via `origin/HEAD`.

### F5 — the OpenSpec contract is unpinned

`gates validate` now shells out to `openspec schemas --json`; the docs carry many
claims about upstream behaviour (regeneration, `--store`, root resolution). Upstream
is pre-1.0 and the fork-staleness episode (`unfork-commands`) already demonstrated
the churn cost. Record the tested OpenSpec version somewhere the shim can check and
warn loudly on mismatch — probe, don't assume.

### F6 — onboarding is six manual steps where one guided command is possible

The honest prerequisite list: git repo, Claude Code + plugin, Node + OpenSpec CLI,
`openspec init --tools claude`, Python 3.9+, a task runner with a real `ci`
command (+ optionally a rules-doc). Streamlining these at **plugin install time is
the wrong moment and likely impossible** — install is per-user and once; every
prerequisite is per-project. The right trigger is the first session inside a given
project, which is the SessionStart hook gatedloop already owns (it already detects
the no-OpenSpec state and offers onboarding). The gap is that `gates-init` stops at
detection: it should become a bootstrapper — check/offer to install the OpenSpec
CLI, run `openspec init --tools claude`, then the existing detect-and-confirm flow,
plus the permission scaffolding harden D4 already assigns to it. Six steps → one
command, run at the moment that has a project in front of it. (Verify at proposal
time that plugins truly have no install-exec hook; the per-project argument holds
either way.)

Scope decisions (2026-08-18, post-review discussion):

- **No scaffold → stop.** In a project with nothing to bind to (no runner, no
  targets), the bootstrapper stops honestly and names what is missing; it never
  invents an oracle. With a scaffold present, it wires everything up and
  *recommends what to populate*.
- **Conventions capture is a core step, not an option.** The crucial onboarding
  moment is populating the conventions that govern generated work. One source
  (the rules-doc, with `Applies to:`/`Rule:` metadata) feeds two consumers: `gates
  conventions sync` → `openspec/config.yaml` `rules:` (governs OpenSpec's artifact
  *authoring*), and `.gates.yaml` `surfaces[].rules` → convention-review (governs
  *code*, enforced per commit; tdd-apply also reads the rules-doc before
  implementing). The bootstrapper harvests existing material (CONTRIBUTING,
  CLAUDE.md, lint configs) into that source, wires both consumers, and runs the
  sync. Open point to verify at proposal time: sync drops `Applies to: code` rules
  by design (no artifact step to deliver them to) — check whether the schema's
  apply block can accept rules before promising code rules inside config.yaml.

### F7 — brownfield gate latency and the greenfield empty-oracle case (deferred)

Two honest limits of "any project", recorded here as candidates material rather
than scheduled work:

- **Brownfield latency/flakiness**: the loop runs `ci` before *every* commit; a
  20-minute or flaky `ci` makes the per-task loop impractical, and nothing in the
  contract speaks to gate cost beyond the unit/ci split. The eventual ledger
  (harden D7/D8, `duration_ms`, `attempt`) is the evidence base for any tiering
  design — defer until it lands.
- **Greenfield**: `gates-init` detects existing targets; a greenfield project has
  none. gatedloop cannot author the oracle (that names stack commands — the
  rejection test says not ours). **Resolved (see F6 scope decisions): the
  bootstrapper stops honestly when there is nothing to bind to** — it names the
  missing prerequisites rather than owning the conversation that builds them.

The integration process (2026-08-18, post-review discussion): the loop assumed a
local squash-merge where teams may require PRs and approvals. Onboarding asks which
process the project uses — preset options, detected default, never auto-bound — and
records it in `.gates.yaml`; the loop and hooks then bind to the declaration instead
of an assumption.

Recommended sequence: `fix-change-scope-selection` → `onboarding-asks-first` →
`harden-unattended-loop` → `streamline-onboarding` → `workflow-packs`. The selection
fix is small and unblocks the marker design; onboarding before packs because packs
assume a project that got through setup.

## Field run — 2026-08-19

On 2026-08-19 the plugin was installed and `/gatedloop:gates-init` run against a
real brownfield project. `streamline-onboarding` (the F6-residue follow-on named
in the Disposition table above) is not yet proposed, so this section only records
what the run produced — evidence for that change, not the change itself.

### FR1 — F6's offer-don't-pick working in the field

`gates-init` detected a `just`-based project, *offered* the detection rather than
binding it, and — once confirmed — produced a valid manifest with real reasoning
behind each binding, not template defaults:

- `unit` bound to the three cheap steps, explicitly excluding the docker build.
- `verify` bound to bring the stack up, then poll `/health` before running the E2E
  suite — because the up command returns before the services actually accept
  requests, a distinction the detector had to reason about rather than template.
- `eval` deliberately left unbound: its recipe takes required positional args with
  no project-wide default, so binding it would have been a guess.

The integration-process question (§5 of `onboarding-asks-first`) was asked, and the
project's actual answer was detected rather than assumed. This is F6 as landed
working end to end against a real, non-trivial project.

### FR2 — the conventions gap, live (evidence for the F6 residue)

The rules-doc was created fresh from the template, so every surface's `rules:`
fell back to inline prose rather than rule-ids. That is correct behaviour — binding
a non-existent rule-id would fail `gates validate` loudly rather than silently —
but the practical effect is that convention review has nothing checkable to
enforce until conventions capture lands. The generated manifest wrote the
`conventions.rules-doc` block commented out, with instructions to uncomment once
real `### <id>` headings exist. This is exactly the gap F6's scope decisions
assigned to the bootstrapper, confirmed against a real project rather than argued
from first principles.

### FR3 — harvest material demonstrably exists in the wild

That project's `openspec/config.yaml` `context:` block already contained real,
checkable conventions that nothing had harvested into a rules-doc: a
components-library-first UI rule, an explicit "use this auth client, not that one"
rule with its reasoning recorded, a mandatory mobile-first rule, a data-fetching
rule forbidding raw `fetch` in component bodies, and a query-key naming
convention. This is the concrete argument that the bootstrapper's harvest step
(F6 scope decisions: "harvests existing material... into that source") has real
input to work with, not a hypothetical one.

### FR4 — `openspec init --tools claude` overwrote local edits with no real prompt

Re-running `openspec init --tools claude` overwrote three locally-edited generated
files (203 insertions, 91 deletions) with nothing beyond a warning — no diff, no
confirmation gate. Recoverable here only because the tree happened to be clean
first. The durable answer is not a gatedloop-side safeguard against an upstream
command's behaviour; it is guidance to fork a schema rather than edit a generated
one (`openspec schema fork <source> <name>`), which `streamline-onboarding` should
say plainly rather than let adopters discover the hard way.

### FR5 — RESOLVED: dropping `code`-scoped rules from sync is correct by design

F6's scope decisions flagged the open point: whether `gates conventions sync` can
deliver `Applies to: code` rules into `openspec/config.yaml` at all, or whether
they are dropped for want of an artifact step to attach them to. Checked against
the code, the schema, and a real CLI run rather than argued from first
principles — verdict: **correct by design, not a defect.** `code`-scoped rules
already reach their actual consumer (convention-review) through the *other* path,
which never touches `config.yaml`; sync dropping them from the artifact-authoring
path is the absence of a home, not a bug losing content.

**What `gates conventions sync` does.** `build_rules_by_artifact`
(`bin/gates:417-431`) groups each rule under every artifact id its `Applies to:`
line names, filtered by `if aid in by_artifact` — and `by_artifact`'s keys are the
*active schema's* artifact ids, resolved at run time from `openspec schemas
--json` (`_schema_artifact_ids`, `bin/gates:543-555`), never a hard-coded set. The
function's own docstring already states the intended behaviour: "`code`-only rules
... are dropped — OpenSpec has no artifact step to deliver them to." `cmd_conventions_sync`
(`bin/gates:608-642`) writes only what that function returns.

Demonstrated, not just read: a scratch fixture (`docs/conventions.md`-shaped rules
source, three sections — a `code`-only rule, a `proposal`-only rule, and a rule
with `Applies to: proposal, code`) run through this repo's own `bin/gates
conventions sync` against a `spec-driven`-schema `openspec/config.yaml` produced:

```
schema: spec-driven

rules:
  proposal:
    - "State the why in one paragraph."
    - "Name the affected surface explicitly."
```

The `code`-only rule left no trace anywhere in the output. The mixed rule's
`proposal` half was written normally and its `code` half was cleanly omitted —
the source text and the other target were untouched, i.e. omission, not
corruption. `exit 0`.

**Whether `config.yaml`'s `rules:` can hold a `code` key at all.** Shape-legal but
functionally inert. The installed CLI's own schema (`@fission-ai/openspec@1.8.0`,
`dist/core/project-config.js:35-40`) types `rules` as `z.record(z.string(),
z.array(z.string()))` — any string key parses. But `validateConfigRules`
(`project-config.js:335-345`) treats a key matching no artifact in *any* available
schema as a warning, not an error, and `instruction-loader.js:154` only ever reads
`projectConfig.rules[artifactId]` for the artifact currently being authored —
`code` is never that artifact id for any schema, so a hand-written `rules.code:`
entry would sit dead even if present. Confirmed live, not just read: a real
`openspec init`'d project with `rules: { proposal: [...], code: [...] }`
hand-added to `config.yaml`, then `openspec instructions proposal --change
demo-change --json` (exit 0) — stderr printed `Unknown artifact ID in rules:
"code". It matches no artifact in any available schema. Known artifact IDs:
design, proposal, specs, tasks`, and the returned `rules` array held only the
`proposal` entry. OpenSpec itself refuses to deliver a `code` rule to any
artifact's instructions.

**Whether an `apply` block can carry rules.** No — checked, not assumed. The
bundled `spec-driven` schema's `apply:` block (`schemas/spec-driven/schema.yaml:205-211`
in the installed package) has exactly `requires`, `tracks`, `instruction`. The
CLI's own parser enforces this uniformly for *every* schema.yaml, built-in or
forked: `loadSchema`/`parseSchema` (`dist/core/artifact-graph/schema.js:13-23`)
run every schema file through `SchemaYamlSchema.safeParse`, whose `apply` field is
`ApplyPhaseSchema` — `requires`/`tracks`/`instruction` only, `z.core.$strip`, so an
unrecognized key (a hypothetical `rules:` under `apply:`) is silently stripped on
parse, not preserved and not an error. Checked against all five community schemas
too (`intent-driven-dev/openspec-schemas`, fetched via `gh api`,
2026-08-19): `behaviour-driven`, `event-driven`, `intent-driven`, `minimalist`, and
`spec-driven-with-adr` all ship an `apply:` block with only
`requires`/`tracks`/`instruction` (`minimalist` omits `instruction` too) — none
declares a `rules` key, and the parser would strip it if one did. None of the six
schemas (bundled + five community) declares a `code` artifact id either. There is
no artifact-land home for a `code`-scoped rule, anywhere in the current OpenSpec
schema ecosystem.

**Why this is correct, not a defect.** `code`-scoped rules are not stranded —
they already reach their real consumer by a path that never goes through
`config.yaml` at all. `.gates.yaml` `surfaces[].rules` feeds `gates rules`
(`bin/gates:847-864`), which the convention-review agent calls directly: it
collects the hot surfaces' rule-ids and resolves them against
`conventions.rules-doc` with no filtering by `Applies to:` and no dependency on
`cmd_conventions_sync` or `config.yaml` having run at all. A `code`-scoped rule-id
listed in a surface's `rules:` works today, un-synced. Sync's job is narrower than
"deliver every rule everywhere" — it delivers the subset that has an
artifact-authoring home, into the one file that can hold it in OpenSpec's shape.
Dropping the rest is the correct behaviour of a generator with no destination for
that content, exactly as `build_rules_by_artifact`'s docstring already says.

**What this means for `streamline-onboarding`.** It can keep the two-consumers
architecture — it is real and it is sound — but it cannot write "one source feeds
two consumers" as if both consumers receive the same content. The accurate claim
is: one source, two consumers, each reading a different projection of it — the
rules-doc entire for convention-review (via rule-id, unfiltered), and only the
artifact-scoped subset for OpenSpec authoring (via sync, `code` excluded by
design). `streamline-onboarding`'s conventions-capture step should state that
boundary explicitly when it documents the bootstrapper's `gates conventions sync`
call, so an adopter reading `Applies to: code` in their own rules-doc does not
expect (or go looking for) a `code:` entry in `config.yaml`.

No defect was found — sync neither produces invalid output nor corrupts a rule; it
cleanly omits the part it has nowhere to put. Nothing here is left open.
