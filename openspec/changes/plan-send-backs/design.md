# Design

## Context

See proposal.md for the motivation. The relevant current state in `bin/gates`:

- **Halt causes (escalation-outcomes, #23).** `HALT_CAUSES` is the one closed set; `_escalation_refusal` validates a cause against it, demands `--detail` for `other`, and writes nothing on a refusal; `_append_escalation_row` writes the row; `outcomes_from_rows` counts every cause, zeros included, and counts a row with an unknown cause as `malformed_halts` in `data_quality`. An `intervention` row stores its kind in the same `cause` field: escalation-outcomes D2 chose one discriminator field for both row kinds.
- **The plan loop's rows (plan-preflight D4, D5).** `plan-round` rows are the loop's counter, not just its record: `_plan_loop_position` counts `open` rows and starts a new loop at each `resume`, `_plan_open_round` treats the last `plan-round` row as the open round when its outcome is `open`, and `_plan_current_loop_rows` slices at the last `resume`. `plan-review` rows carry a checker's verdict (`clean`, `findings`, `question`). `gates plan resume` writes a `resume` row whose `detail` is the planner's summary of what was decided. All of them are in `NON_GATE_EVENTS`, filtered out of `stats_from_rows`, and read by nothing outside `gates plan`.
- **The row shape.** `LEDGER_ROW_FIELDS` is the union of every row kind's fields, written in full on every row; a new field is appended under the union rule and keeps `LEDGER_ROW_VERSION` at 1 (stability-contract D1).
- **`gates stats`.** `cmd_stats` resolves the scope (current branch, `--change`, `--all`) and fails loud on a missing ledger, then hands the rows to a pure aggregator: `stats_from_rows` for economics, `outcomes_from_rows` and `outcomes_aggregate` for `--outcomes`. `--outcomes` and `--cost` are independent flags today, and `--epic` short-circuits before both.
- **The propose path.** `loop.plan-preflight` defaults to `skip`, so most adopters run no plan loop and write no plan rows; the plan's ledger is committed with the plan only when the loop wrote rows. A human's answer reaches the ledger only through `gates plan resume --reason`, and a PR review that requests changes reaches it only when the planner chooses to resume.

## Goals / Non-Goals

**Goals:**

- A send-back before approval is a row with a sender, a class from a closed set and the sender's exact words, written by the shim and refused when it cannot be classified.
- `gates stats --plans` answers "why do plans come back, who sends them, which kinds recur" from those rows, beside the loop's own checker returns.
- Nothing that reads the ledger today changes its answer.

**Non-Goals:**

- Detecting send-backs automatically (a forge webhook, polling PR reviews). The row is written by whoever acts on the send-back, as a halt is written by the lane that halts. A hook can come later; `docs/candidates.md` gets the entry.
- Making the send-backs of a plan PR that is closed without merging visible from the target. Its rows live on its plan branch; `gates stats --plans` reads the checkout's ledgers and says so in its closing note. The candidate entry records this too.
- Judging whether the class is right. The planner (or whoever records) chooses it; the words sit beside it, so a mislabel is visible in `gates plan status` and the raw rows.

## Decisions

**D1. A new row kind, `plan-returned`, not an extension of `plan-round`.** Four reasons, the first decisive:

1. `plan-round` rows drive the loop. `_plan_open_round` reads the *last* `plan-round` row, so a send-back written as a `plan-round` row during an open round would close the round; `_plan_loop_position` and `_plan_current_loop_rows` would need a new outcome excluded everywhere they count. A separate event name is invisible to all three with no change to them.
2. Most send-backs happen with no loop at all: `loop.plan-preflight` defaults to `skip`, and a PR review comes after a green loop as often as during one. A `plan-round` row without a loop or a round would be a row of the counter that counts nothing.
3. A send-back does not always restart the loop. A `nit` is amended and pushed, with no resume; a closed PR is never resumed. The two facts are separate, so they are separate rows, linked when they coincide by D4.
4. It matches the precedent the issue names: a halt is its own event, not an outcome of `task-start`.

Alternative considered: a new `outcome: returned` on `plan-round`. Rejected for reason 1: every reader of `plan-round` would have to learn to skip it, and a reader that forgot would miscount the budget, which is the shim's own guarantee.

**D2. The row's fields.** `gate: "plan-returned"`, `change`, `ts`, `by`, `cause` (the class), `detail` (required for `other`), `words`, `ref`, `plan_sha`, `tasks_sha`, `loop`; `exit`, `task`, `tree` and the other fields are `None`. Three fields are new and appended to `LEDGER_ROW_FIELDS` under the union rule: `by`, `words`, `ref`. The class goes in the existing `cause` field, as an intervention's kind does (escalation-outcomes D2: one discriminator, so a reader that groups rows by `cause` handles every escalation-like row the same way, and every row of 12k-row ledgers is not widened by a fourth field). The CLI flag is `--class`, and `gates plan status --json` and `gates stats --plans --json` name it `class`: the field name is the ledger's, the vocabulary is the issue's. `plan_sha` and `tasks_sha` come from `_plan_digests`, the same digests the loop's rows carry, so a send-back can be joined to the round that checked the same content. `loop` is `_plan_loop_position`'s current loop, for the same join. `words` is stored exactly as given, never stripped or rewrapped; only an empty or all-whitespace value is refused. Because a shell argument cannot carry arbitrary text verbatim (a `"`, `$`, backtick or newline is altered or breaks the command), the writer also takes `--words-file <path>`, whose content is read as UTF-8 and stored exactly, trailing newlines included; a file that does not decode as UTF-8 counts as unreadable. Exactly one of `--words` and `--words-file` is required; both, or an unreadable file, is refused with exit 1 and nothing written. The prompts always use `--words-file`. `ref` is free text, because a send-back in a chat or a terminal has no URL.

**D3. Two closed sets, validated like halt causes.** `PLAN_RETURN_SENDERS = ("human", "reviewer")` and `PLAN_RETURN_CLASSES = ("scope", "approach", "spec-gap", "decision", "collision", "drift", "safety", "nit", "other")`, defined once beside `HALT_CAUSES`, with the one-line meanings the `plan-returns` closed-set requirement gives (`safety`: a risk to data, security or a project's work; `nit`: wording or presentation only; `other`: none of these, its detail saying what). The writer reuses `_escalation_refusal` for the class (with `other` requiring detail), and `_escalation_noun` gains a `plan-returned` branch returning `class`, so the refusal reads "a plan-returned with class '<value>'"; the sender is refused with the same message shape and the noun `sender`; a refusal exits 1 and writes nothing (`fail-loud-gates`). The issue's third sender, `checker`, is left out on purpose: a checker's send-back is already a `plan-review` row with verdict `findings` or `question`, so a `checker` send-back row would record the same event twice and the stats would double-count it. `gates stats --plans` reads checker returns from those rows instead (D6).

**D4. `gates plan returned`, and the resume feed.** `gates plan returned <change> --by --class --words|--words-file [--ref] [--detail]` requires the change's directory (`_plan_require_change`) and nothing else: no open round, no preflight mode, no branch. `gates plan resume` gains the same six flags. If any of them is given, `--by`, `--class` and one of `--words` or `--words-file` are all required, so `--ref` or `--detail` alone is refused with exit 1 naming the three, never silently dropped; everything is validated before the first write, so a refusal leaves neither row. Then the `plan-returned` row is appended, then the `resume` row, in that order, so file order says the send-back caused the resume. `--reason` stays required and keeps its meaning (what was decided, in the recorder's words); `--words` is what the sender said. The resume feed's `plan-returned` row takes `_plan_digests` from the working tree when it runs, so it is for a send-back recorded before any amendment; the shipped prompts do not use it (D9). Alternative considered: making the resume's `--reason` the words. Rejected: the reason is the planner's summary by design, and the issue's complaint is exactly that a paraphrase is all the ledger holds.

**D5. `gates plan status` lists send-backs, and its state is untouched.** `_plan_status_doc` gains `returns`: the `plan-returned` rows in file order, each `{by, class, detail, words, ref, plan_sha, tasks_sha, loop, ts}`. The text and `--markdown` forms print a "sent back" list straight after the last loop's lines, before the moved-digests note and the preflight snapshot line, one line per row with the words beneath it. The text form's heading is `sent back:` and each row's line is `  <by> · <class> · plan <plan_sha[:12]> · <ref, or - when absent>`; the markdown form's heading is `**Sent back**` and each row's line is ``- **<by>** · <class> · plan `<plan_sha[:12]>` · <ref, or - when absent>``. Tests assert these strings. Words keep their line breaks, split with `splitlines()`, so a trailing newline adds no line: in `--markdown` every line of the words is prefixed with `> ` (an empty line becomes `>`), so a multi-line send-back stays one blockquote; in the text form every line is indented by six spaces. With no rows they print exactly what they print today. `_plan_rows` keeps returning only the loop's two row kinds, so the state, the rounds and `green_round_moved` are computed from the same rows as before.

**D6. `gates stats --plans`, a third view beside economics and outcomes.** Same structure as `--outcomes`: `cmd_stats` resolves the scope and fails loud as it does today, then `_plans_report` reads each change's rows and hands them to a pure `plans_from_rows(rows)`, with `plans_aggregate(per_change)` for `--all`. `plans_from_rows` also returns a per-change `months` map (each `YYYY-MM` of a well-formed, dated send-back to a map of every class, zeros included), which `plans_aggregate` sums into `trend` and `_plans_report` drops before output, so the per-change shape stays exactly as pinned. Per change: `returns` (count of well-formed `plan-returned` rows), `by` (every sender, zeros included), `class` (every class, zeros included), `checker_returns` (`plan-review` rows with verdict `findings` or `question`, keyed by `checker`, holding only checkers with at least one such row, no zeros, since lens ids vary per project; `dry-run` is counted like any other checker; the shim-recorded `plan-check` is always clean and never appears), `resumes` (`plan-round` rows with outcome `resume`), `first_ts` (the earliest well-formed send-back's `ts`, or `None`). A malformed send-back (sender or class missing or outside its set) counts only in `data_quality.malformed_returns`: it is excluded from `returns`, `by`, `class`, `first_ts` and the trend. A well-formed send-back without a usable `ts` counts in `returns`, `by` and `class` but not in `first_ts` or the trend, and in `data_quality.rows_without_ts`. The aggregate sums those and adds `trend`: a map from each `YYYY-MM` (of a send-back's UTC `ts`) with at least one well-formed, dated send-back to a map of every class, zeros included. `data_quality`: `unparseable_lines`, `rows_without_ts` (send-back rows only, since only they are dated in the trend), `malformed_returns`. JSON is one `sort_keys` document with the same three top-level keys under any scope, as `--outcomes` is. The human form mirrors `_outcomes_format_human`: per change, `=== <change> ===`, then `returns:         <n>`, `by sender:       human <n>, reviewer <n>`, `by class:        <class> <n>, ...` (every class, in closed-set order), `checker returns: <checker> <n>, ...` (sorted by checker, or `none`), `resumes:         <n>`, `first send-back: <first_ts, or unknown>`, and a blank line; under `--all`, `=== all changes ===` followed by the `returns`, `by sender`, `by class`, `checker returns` and `resumes` lines summed (no `first send-back` line), then one `trend <YYYY-MM>: <class> <n>, ...` line per month in order; then, once, the disclosure line `data quality: <u> unparseable line(s) skipped, <t> send-back row(s) had no usable timestamp, <m> malformed send-back row(s)`, and the closing note on what the ledger cannot see, which reads exactly: `Send-backs are counted only where someone recorded them, and only on the ledgers this checkout holds: a plan PR closed without merging keeps its rows on its plan branch.` Tests assert that sentence. `--plans` with `--outcomes`, `--cost` or `--epic` exits 1 before reading anything; `--idle-gap` is accepted and ignored, as it is under `--outcomes`.

Alternative considered: folding send-backs into `--outcomes`. Rejected: outcomes measure the lane after approval (hands-off share), and a plan sent back three times before approval says nothing about whether its lane ran hands-off. Mixing them would change the north-star number for every adopter who records send-backs.

**D7. The existing views ignore the new rows.** `plan-returned` joins `NON_GATE_EVENTS` and the filter at the top of `stats_from_rows`, so economics are byte-identical. `outcomes_from_rows` drops `plan-returned` rows before its loop, so a send-back is never a first activity, never a row without a session, never an intervention. It does not also drop `plan-round` and `plan-review` rows: they already move `first_ts` today, and changing that is a different change with its own test churn.

**D8. Opt-in through `loop.plan-returns: record | skip`, default `skip`.** The shim's new surfaces change nothing until someone runs them, so they need no key. The prompts are different: under the new instruction, a planner would start appending rows, with people's words in them, to a ledger that is committed with the plan and visible in the plan PR, in projects whose plan PRs today carry no ledger at all. That is adopter-facing, so it is opt-in (maintainer rule: new behaviour is opt-in unless the plan says otherwise). `record`/`skip`, not `on`/`off`, for the reason `loop.plan-preflight` gives (PyYAML reads `on` as `True`, `_mini_yaml` as `"on"`). It joins `LOOP_KEYS`, is validated in `_errors` (an unknown value fails naming the key and both values), is described in the schema, and is offered by `/gatedloop:upgrade` through a `plan-returns` catalogue item (`since: "0.14.0"`, applies to every project, detector and action `manifest-key` on `loop.plan-returns`). The prompts read it from `gates plan check <change> --json` as `returns`, as they read `preflight` there, so no prompt parses YAML.

**D9. What the prompts do under `record`.** `commands/propose.md` and `commands/planner.md`: when a human or a non-checker session sends the plan back (an answer to a recorded question, a human's decision after a stall that changes the plan, requested changes on the plan PR, a defect found in review, a closed PR), the prompt records it **before amending**, whatever `preflight` is, always with `gates plan returned`, so the row carries the digests of the content that was sent back (D2's join). The sender's exact words (copied, never paraphrased) are first written to a file in the session's scratch space with the host's file-writing tool, never through a shell argument, then recorded with `gates plan returned <change> --by human|reviewer --class <class> --words-file <file> --ref <PR or comment URL when there is one>`. The prompt lists the nine classes, each with its one-line meaning from the `plan-returns` closed-set requirement, and says `other` needs `--detail`. Then the prompt amends; when a loop resumes (step 5g, or an update that moved the digests), it runs a plain `gates plan resume`, as today. The prompts never pass the send-back flags to `gates plan resume`: the resume feed (D4) is for a person recording by hand before any amendment. A stall is the loop's own return, not a send-back: a human's decision to resume a stalled loop unchanged records nothing, and one that changes the plan is recorded with the class it fits. A closed PR has no amendment: when a person tells the session the plan PR was closed without merging, the prompt records the send-back, commits the ledger to `plan/<name>`, pushes it and stops, with no step 7; this is a new last sentence of propose's "on an update to an open plan PR" paragraph, which the planner's new bullet points to. Step 5's `skip` exit changes so that, on an update to an open plan PR, or when told the plan PR was closed without merging, it first records the send-back as above; for an update it then goes to step 6, and for a closed PR it commits the ledger, pushes `plan/<name>` and stops, so both are reached under `preflight: skip` too. Step 6 stages `.gatedloop/runs/<name>.jsonl` whenever the file exists, whether it holds loop rows, send-back rows or both, so a ledger holding only send-backs is committed and pushed with the plan. In `commands/planner.md`, the line for a send-back in review is a new bullet in step 2 after **stalled**, reading: "**sent back in review**: on requested changes on the plan PR, a defect a non-checker session reports, or the plan PR closed without merging, follow `/gatedloop:propose`'s 'on an update to an open plan PR' paragraph, which records the send-back under `returns: record`." A checker's finding is never recorded this way (D3). Under `skip`, nothing is recorded and the prompts behave as today.

## Risks / Trade-offs

- [An older plugin reads a ledger holding `plan-returned` rows] → It does not know the event, so its `gates stats` counts the row as a gate run with no exit and no duration: a zero-duration gate row with an unknown name. The same was true of `plan-round` rows before 0.12.0, and stability-contract D1 bumps the row version only when a row's meaning changes, not for a new kind. Accepted; the row version stays 1.
- [The recorder mislabels the class] → The words sit beside the class in the row, the status and the JSON; `other` with detail is always available, so nobody is forced to mislabel.
- [Words hold something sensitive] → The ledger is committed and pushed. The prompts quote the send-back that is already on the plan PR or in the session; the adoption question says the words land in the committed ledger, so an adopter decides with that in view.
- [Overlap with `approved-tests` and `review-provenance`] → All three append to `LEDGER_ROW_FIELDS` and to the exact field sets the suite pins (`tests/test_ledger.py`, `tests/test_task_baseline.py`, `tests/test_review_record.py`, `tests/test_audit.py`); `review-provenance` also adds a `loop` key and a catalogue item, and `approved-tests` edits the same two prompts. Each is an append or a separate paragraph, so whichever merges second rebases with a textual conflict at most, never a semantic one.

## Migration Plan

Additive. Ledgers written before this change hold no `plan-returned` rows and report zero send-backs. Projects that never set `loop.plan-returns` see no prompt change; `/gatedloop:upgrade` asks them once. Rollback is removing the key; the rows already written stay readable and ignored by every other view.
