# Proposal

## Why

The test author is the first agent that reads a plan against the real code, and it runs only after the plan is approved. Every gap it finds then costs a halted lane, a plan amendment and a second approval. #168 reports this from an adopter under 0.11.1: most of its plan PRs over two days were amendments made after approval. The causes were handoff refusals and failed test-quality reviews, plans that were wrong about the code, a task order that deadlocked, and plans that drifted while they waited to be handed off. Nothing in the propose path checks a plan before a person approves it. The shim already refuses most of the specific defects, but only at handoff, after approval.

A one-shot advisory check whose output is thrown away would move some of these findings earlier. It would not stop the planner from asking for approval on a plan that still fails them. So this change gives planning a loop of its own that ends in a verdict, as implementation already has.

## What Changes

- **A plan loop, run by the planner before the plan PR asks for approval.** The planner holds the deep context. Fresh-context checkers each read the plan cold. One round is: draft or amend, then `gates plan round` (which runs the free static checks), then **plan review** through each lens, then the test author in preflight mode, then `gates tests handoff --dry-run`, then the authored-set convention review. Any finding goes back to the planner, who amends the plan, and the next round starts. The loop exits in one of three ways: **green** (every step clean, so only implementation remains); **question** (something only a human can answer, recorded with its options); or **stalled** (the round budget, default 3, is spent).
- **The loop's depth scales with blast radius, in three layers.** First, **a floor computed in `bin/gates`:** `full` when any one deterministic signal is high. The signals are the number of tasks, the number of files and of surfaces the plan names, a spec delta that modifies, removes or renames an existing requirement, and a hot surface declared `blast-radius: high`, which is how an adopter marks its public contract. Second, **a classifier that may only raise the tier:** effective tier = max(floor, classifier). Its contract is typed answers, so a classifier that returns no prose fits it. The classifier answers narrow blast-radius dimensions (security path, persisted data, public interface, irreversible operations, and an overall tier). These live in the shipped data file `rules/plan-tier-dimensions.json` and are overridable in the manifest, and the shim combines the answers deterministically. Confidences are recorded, and the reason is optional. The input is `{digest, dimensions}`, where the digest is a bounded summary that the shim builds (`gates plan digest`) and trims from the bottom to the adopter's `classifier-input-limit`. A plan too large to fit even its signals, paths and spec headers is `full` with no call. The output is validated against the shipped `schema/plan-tier.schema.json`. The adopter may bind an external command, its own adapter, with `loop.plan-preflight.classifier`. The shim ships no vendor client and never reads a secret, and declaring a classifier sends the digest to a third party, which the adoption question says. Without a classifier, or when it fails or times out, the built-in `gatedloop.blast-radius` lens answers the same dimensions in the same JSON, and the fallback and its cause are recorded. Third, **overrides that are never silent:** raising is free (`--tier full`, or a `Plan tier: full` line), and lowering needs a `Plan tier: light — <reason>` line in the proposal or design, which the approval covers. `gates plan tier <change>` prints every layer. **light** is `gates plan check` plus the implementability lens, in one pass. **full** is the whole loop.
- **A new shipped agent, `agents/plan-review.md`** (Opus, read-only). A plan review is rarer than a diff review and a miss costs a halted lane and a second approval, so it runs on the stronger model. It reads the plan's artifacts and only the code the plan names, and judges through one lens per run. Every finding cites a lens id and a check number. It is stack-agnostic.
- **Built-in lenses in `rules/plan-lenses.md`,** next to `rules/loop-rules.md`. They are `gatedloop.implementability` (named paths, rules, commands and configuration exist and say what the plan assumes; no task needs an artifact that a later task creates) and `gatedloop.zero-decision` (no task leaves a design decision to the implementer; every behaviour change has a spec scenario and a matching oracle tag). A lens is an id plus its rules, and `gates plan brief` selects the lenses deterministically, so a later change can bind lenses per surface without reworking the agent.
- **The loop's output persists across rounds and machines, outside the plan.** The author writes to a per-worktree, git-ignored store, `.gatedloop/out/preflight/<change>/`. It holds the authored tests, a digest per task of the brief content that task was authored from, the classifier verdict and each round's reports. `gates plan save <change>` snapshots it to its own branch, `gatedloop/preflight/<change>`, whose tree holds only the store, and the planner pushes that branch with the plan branch. `gates plan restore <change>` rebuilds the store from that branch on any machine or fresh worktree. The plan PR stays plan-only, and nothing in the store reaches `main`. A later round's brief names only the tasks whose inputs changed, and the author re-authors only those. Bringing the held set into the implementation is `approved-tests`' job.
- **A provenance record, never a gate.** `gates plan round`, `gates plan record` and `gates plan resume` append `plan-round` and `plan-review` rows to the change's ledger. Each row carries the round, the plan digest (the same digest the approval pins), the tier, and the checker with its verdict. The planner commits these rows with the plan. `gates plan status <change> --markdown` renders them for the PR body. Nothing in approval, handoff or merge reads them. The shim counts rounds from these rows, and `gates plan round` refuses to open a round past the budget, as the attempt budget does.
- **Kept from the earlier plan:** `gates plan check <change> [--against <ref>] [--json]`, with the change's oracle-tag findings, untagged tasks under `required`, a `rewrites:` path absent at the base (naming the earlier task that creates it), and drift at handoff. Also kept: `gates tests brief --preflight`, `gates tests handoff --dry-run` (the real refusals, no `tests-handoff` row and no git object, with the tag-drift comparison skipped and that skip printed), and `gates tests show --preflight`.
- **Held tests are never committed off a change branch.** `gates tests check` refuses a staged path under `.gatedloop/authored/` whenever the branch resolves to no active change.
- **`loop.plan-preflight`**: `run` or `skip`, default `skip`, either as a scalar or as a mapping `{mode, rounds, full-at: {tasks, files, surfaces}, classifier, classifier-timeout, classifier-input-limit, dimensions}`. `gates validate` refuses `run` together with `loop.test-author: inline`. `gates plan check` runs whatever the key says. Surfaces gain an optional `blast-radius: high | normal` key.
- **Prompts.** `commands/propose.md` runs the loop at the computed tier, and opens the plan PR as a draft unless the loop ended green. `commands/planner.md` makes the loop part of the planner's job. On its own plan branch, the planner dispatches plan review, the test author in preflight mode and the authored-set review. `agents/test-author.md` gains a preflight mode, and `agents/convention-review.md` reads `--preflight`.
- **Adoption item** `plan-preflight` (`since: 0.12.0`). Its cost is stated in usage terms. **`docs/candidates.md`**: the elephant-goldfish entry is rewritten, because this change adopts its loop as ours.

**No guarantee moves.** Approval, attestation, `gates handoff`, the real `gates tests handoff`, the lock and `gates merge` are unchanged. The loop's verdicts are LLM judgements, so they are recorded and shown to the approver, and never block.

## Against the rejection test (with the boundary revised)

- **Does it author an artifact?** No. The planner, through `/opsx:propose`, still authors every artifact. The loop judges a plan and hands its findings back.
- **Does it know a stack command?** No. The prompts name only `gates …`, gate names and lens ids. No shipped prompt or code names a classifier vendor or model: an external classifier is a command the adopter binds, as a gate is. Per-surface lenses, which might encode stack knowledge, are left to the adopter's manifest in a later change.
- **Does it make a stated guarantee enforceable?** Yes. "An approved plan is one the loop can implement" becomes something checked before approval, with a recorded verdict, instead of something discovered at handoff.
- **Does it get a team running faster?** Yes. It removes the amend-and-re-approve round trip that 20 of 24 field plans paid.

**This deliberately revises an earlier boundary.** `docs/candidates.md` recorded that judging a design is "not ours". It is ours now, for the reason the single question gives: the loop moves the planning phase from `act` to `close`. Until now gatedloop closed implementation, and planning ended at "a human read it". The evidence is an adopter's plans, most of them amended after approval. Authoring stays out: the loop never writes a plan, it returns findings to the planner.

## Capabilities

### New Capabilities

- `plan-preflight`: the plan loop and its exits, the tier (floor, classifier slot and overrides), the plan-review agent and its lenses, the preflight store and its reuse across rounds, the provenance rows and the round budget, `gates plan check` and its drift mode, the dry-run handoff and the preflight view, the opt-in key, the `blast-radius` surface key, and the refusal of held tests staged off a change branch.

### Modified Capabilities

- `command-surface`: the planner role runs the plan loop as part of its job, on its own plan branch, and runs the drift check before it sends a handoff.
- `upgrade-adoption`: the `plan-preflight` adoption item.

## Impact

- `bin/gates`: a `plan` subcommand group (`check`, `tier`, `digest`, `classify`, `brief`, `round`, `record`, `resume`, `status`, `save`, `restore`), a stdlib validator for the classifier's output, `tests brief --preflight`, `tests handoff --dry-run`, `tests show --preflight`, the `loop.plan-preflight` key and the `blast-radius` surface key with their validation, the `plan-round` and `plan-review` row kinds, and a refusal in `tests check`.
- New shipped files: `agents/plan-review.md`, `rules/plan-lenses.md`, `rules/plan-tier-dimensions.json` and `schema/plan-tier.schema.json`.
- `schema/gates.schema.json`, `adoption/catalog.json`, `tests/contract.json`, and this repository's `.gates.yaml` (a `contract` surface marked `blast-radius: high`).
- Prompts: `agents/test-author.md`, `agents/convention-review.md`, `commands/propose.md` and `commands/planner.md`.
- Docs: README.md, SETUP.md, AUTOMATION.md, `docs/running-at-scale.md` §8 and `docs/candidates.md`.
- In-flight changes: `review-provenance` writes no row on a `plan/*` branch and its row kinds are `review` and `review-provenance`, so the new kinds cannot collide. Its reviewer Bash allowlist admits `gates tests show` with any flags, so `--preflight` stays inside it. `checkable-disputes`' `--defend` composes with `--dry-run`, because a dry run records no defence.
- Compatibility: the loop is opt-in. An unset key leaves the propose path as it is, apart from `gates plan check`, which reports only what the handoff would refuse anyway.
