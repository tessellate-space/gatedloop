# Proposal: acceptance-gate

## Why

Issue #25: the factory has three human gates — approve the spec before the loop,
accept the working increment after it, and answer an escalation — and the two are
built to very different standards. The *before* gate is attested from a real
approving review, content-pinned, and the model cannot write it
(`loop-enforcement`, "Approval is attested from the forge, never self-reported"). The
*after* gate is a merge click: an `ask` permission rule on `git merge`, a JSON block of
gate statuses, and the words `READY TO MERGE`. Nothing shows the human the *behaviour*
they are accepting, and nothing records that anyone accepted it. The design memo
already names the gap — *"Missing: the single artifact a human approves"*
(`docs/specloop-map.html`, Part 5).

This matters for more than symmetry. The north-star metric (issue #23, change
`escalation-outcomes`) ends at *accepted demo*, not *merged*. Without an acceptance
event the metric can only be computed to `merged`, which measures the loop's ability
to satisfy its own oracles, not the human's intent.

## What Changes

- **Acceptance is a declared, opt-in policy** in the existing `approval` block:
  `approval.acceptance: review | self`. Absent means today's behaviour exactly.
  `gates validate` rejects other values and rejects `review` on a project whose
  integration mode has no pull request to review.
- **The acceptance record is a ledger row, not a `.openspec.yaml` key.** Plan approval
  pins a hash of artifact *content*, so writing its keys into `.openspec.yaml` does
  not disturb what it pins. Acceptance pins a *tree*, and writing anything into the
  tree would change the tree it pins. The ledger is already excluded from every
  normalized tree and survives the squash, so it is the one place an acceptance can be
  recorded without invalidating itself. Row: `gate: "acceptance"`,
  `verdict: accept | reject`, the ledger-normalized head tree, and a new
  `accepted_by` field; a `reject` additionally carries a cause (`weak-spec` or
  `missing-oracle`) and detail, reusing `escalation-outcomes`' fields.
- **Attestation writers mirror plan approval exactly.** `gates acceptance attest
  <change> --local` is legitimate only under `self`; `--pr <n>` reads the pull
  request's actual `APPROVED` review and fails closed when the forge CLI is missing,
  unauthenticated or offline. Neither accepts a caller-supplied identity or tree; both
  refuse when the policy is undeclared. `gates acceptance reject <change> --cause
  <weak-spec|missing-oracle> --detail …` records a rejection as an escalation.
- **Merge requires acceptance when the policy is declared.** The merge hook gains one
  O(1) check after taint: an `accept` row whose tree equals the normalized incoming
  tree, with no later `reject` for that tree. The forge merge path is covered the same
  way plan approval is: documented branch protection, now naming the acceptance
  review.
- **The acceptance brief is generated by the shim from data it owns.** `gates
  acceptance brief <change>` prints, in scenario language: every `#### Scenario:` in
  the change's specs; per scenario, `covered` when a same-titled acceptance scenario
  exists under a declared `acceptance.match` glob (the verify skill's Layer 1 rule,
  moved into code) else `check by hand`; the change-level verdicts on the head tree
  from the ledger (`verify`, `live-check`, `integration`, `ci`, latest review); the
  "check these by hand" list; and a footer stating what the brief cannot claim. It is
  deterministic and never LLM-authored — self-reported evidence is what this change
  exists to remove.
- **The loop generates the brief at completion and stops for acceptance where
  declared.** `tdd-apply` §7.5 runs the brief after the live-check and, under a
  declared policy, stops before integration until an `accept` row exists — the same
  boundary as `requireApproval: true`. `tdd-implementer` generates the brief as its
  last act and its report gains `"acceptance": "required" | "not-required"`.
- **`gates stats --outcomes` terminates at acceptance where declared.** Hands-off
  requires *accepted*, not merely merged; `reject` rows count under halts by cause.

## Capabilities

### New Capabilities

- `acceptance-gate`: the acceptance row and its tree pinning; the writers and their
  legitimacy; `gates acceptance check`; the brief's contents, coverage rule,
  determinism and honesty footer; the `acceptance.match` manifest key.

### Modified Capabilities

- `approval-policy`: the block gains `acceptance`; the legitimacy rules for local and
  PR acceptance attestation; the refusal when undeclared; the incompatible-mode
  validation.
- `loop-enforcement`: merge blocked without acceptance under a declared policy; the
  implementer report gains `acceptance`; the forge-path branch-protection requirement
  extends to the acceptance review.
- `gate-economics`: an additional requirement — under a declared acceptance policy the
  outcomes view's terminal event is acceptance.

## Impact

- **Depends on `escalation-outcomes`** (issue #23): reuses its `cause`/`detail` row
  fields, its closed cause set, and its `--outcomes` view. This change's docs and code
  assume that one has landed.
- `bin/gates` — `cmd_acceptance` (`attest --local|--pr`, `reject`, `check`, `brief`);
  `accepted_by` appended to `LEDGER_ROW_FIELDS`; `acceptance` in `NON_GATE_EVENTS`;
  `_acceptance_policy`; validation of `approval.acceptance` and `acceptance.match`;
  `outcomes_from_rows` reads acceptance rows under the policy.
- `schema/gates.schema.json` — `approval.acceptance` enum; top-level `acceptance`
  block with `match`.
- `hooks/gate-merge.sh` — one more check, `gates acceptance check <tree>`.
- `skills/tdd-apply/SKILL.md` §7.5, `agents/tdd-implementer.md` §4 and report,
  `skills/verify/SKILL.md` Layer 1 (points at the shim's rule instead of restating
  it), `SETUP.md` (approval section, branch protection, command reference,
  headless report), `AUTOMATION.md`, `templates/gates.yaml.template` (commented
  example).
- `tests/` — new cases for policy validation, the writers' refusals, tree pinning,
  `check`, the brief's determinism and coverage rule, the merge hook, and the outcomes
  terminal rule; existing approval, merge-gate and stats suites must keep passing.
- Adopters: additive and opt-in. Nothing changes until `approval.acceptance` is
  declared; the brief is available without it.
- Rejection test: authors no artifact (the brief is a generated view, not a plan
  artifact), names no stack command, and makes "a human accepted this behaviour"
  enforceable and attested — a `close` job, ours.
