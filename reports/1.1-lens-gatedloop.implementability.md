question: gatedloop.implementability #1 — design D5 (and Goals: "checkable … at the merge head and at the forge"); tasks 2.2, 4.1 — the `--ref` form of 4b assumes the tree a `gates run` row records can be read wherever `gates tests check --ref` runs. Because the ledger row is staged only after the run (tdd-apply 5h), that tree differs from the tick commit C's tree in the ledger entry, so it is never any commit's tree and is never pushed. In a fresh clone (the forge, `_ForgeRefusal` path), `_normalize_tree(row["tree"])` fails at `read-tree` and returns the raw hash by its fail-strict contract. That hash never equals `_normalize_tree(C^{tree})`, so 4b refuses every clean preserve task there. 4a's start tree (the raw `task-start` write-tree, ~6379) has the same exposure whenever the index at task start was not a commit's tree. How should the --ref form get readable trees? Options: (a) have `gates run --task` and `gates task start` also record the ledger-normalized tree in a new row field, which breaks the proposal's "no … ledger field changes" and changes tests/contract.json; (b) under `at`, derive both sides from commits only: start = the tree of C's first parent (or of the commit carrying the `task-start` row), and the green run = a passing verdict row for the task carried by C, without comparing trees; (c) narrow the Goals and spec "The preserve conditions hold at any commit" to repositories holding the local objects, and have 4a/4b under `at` report "tree not available" as a refusal or a skip, stated explicitly.
